## Which version is current, and what arrived when (4.3 -> 4.7)

### Takeaway
Current stable is Godot 4.7.2 (tag dated 16 Aug 2026); there is no 4.8-stable tag. ## Skeleton3D: data model, API, signals, per-frame processing order, deprecations

### Takeaway
A bone has a rest and a pose (position / rotation / scale, pose includes rest in Godot 4); "global pose" means skeleton-space, not world-space. Animation writes poses; then, once per frame in a deferred `NOTIFICATION_UPDATE_SKELETON`, the skeleton runs every child `SkeletonModifier3D` in child order, emits `skeleton_updated`, pushes transforms to the skins and then rolls the bone poses back to the unmodified (animated) values.

### Cited Findings
- `Skeleton3D` inherits `Node3D`. "The overall transform of a bone with respect to the skeleton is determined by bone pose. Bone rest defines the initial transform of the bone pose. Note that 'global pose' below refers to the overall transform of the bone with respect to skeleton, so it is not the actual global/world transform of the bone." - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml)
- "In Godot 3, Bone Pose is relative to Bone Rest, but in Godot 4, it includes Bone Rest." - [Retargeting 3D Skeletons (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.rst)
- Properties (4.7.2): `modifier_callback_mode_process: int = 1` ("Sets the processing timing for the Modifier"), `motion_scale: float = 1.0` ("Multiplies the 3D position track animation. Note: Unless this value is 1.0, the key value in animation will not match the actual position value."), `show_rest_only: bool = false` (forces rest pose; blocks editing in editor), `animate_physical_bones: bool = true` (DEPRECATED; controls the internal compatibility `PhysicalBoneSimulator3D`'s `active`) - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml)
- Enum `ModifierCallbackModeProcess`: `MODIFIER_CALLBACK_MODE_PROCESS_PHYSICS = 0`, `MODIFIER_CALLBACK_MODE_PROCESS_IDLE = 1` (default), `MODIFIER_CALLBACK_MODE_PROCESS_MANUAL = 2` ("Do not process modification. Use `advance` to process the modification manually"). `MANUAL` and `advance(delta: float)` were added in **4.5** - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml), [4.4 XML for comparison](https://raw.githubusercontent.com/godotengine/godot/4.4-stable/doc/classes/Skeleton3D.xml)
- `advance(delta)`: "Manually advance the child SkeletonModifier3Ds by the specified time (in seconds). Note: The delta is temporarily accumulated in the Skeleton3D, and the deferred process uses the accumulated value to process the modification." - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml)
- Hierarchy API: `add_bone(name) -> int` (index or -1; names unique, non-empty, no `:` or `/`), `find_bone(name) -> int`, `get_bone_name`, `set_bone_name`, `get_bone_count`, `get_bone_parent(bone_idx)` ("The parent bone returned will always be less than bone_idx"), `set_bone_parent(bone_idx, parent_idx)` ("parent_idx must be less than bone_idx"), `get_bone_children -> PackedInt32Array`, `get_parentless_bones`, `unparent_bone_and_rest`, `clear_bones`, `get_version()` ("number of times the bone hierarchy has changed ... Use for invalidating caches in IK solvers"), `get_concatenated_bone_names() -> StringName` (comma-joined, for enum hints) - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml)
- Rest API: `get_bone_rest`, `set_bone_rest`, `get_bone_global_rest`, `reset_bone_pose(bone_idx)`, `reset_bone_poses()`, `localize_rests()`, `create_skin_from_rest_transforms() -> Skin`, `register_skin(skin) -> SkinReference` - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml)
- Pose API: `get_bone_pose(bone_idx) -> Transform3D`, `set_bone_pose(bone_idx, pose)`, `get/set_bone_pose_position` (Vector3; described as "local to the Skeleton3D node" in the XML), `get/set_bone_pose_rotation` (Quaternion, "in the bone's local coordinate space with respect to the rotation of any parent bones"), `get/set_bone_pose_scale`, `get_bone_global_pose(bone_idx) -> Transform3D` (skeleton-space), `set_bone_global_pose(bone_idx, pose)` ("If other bone poses have been changed, this method executes a dirty poses recalculation and will cause performance to deteriorate. - Important note on getters: `get_bone_pose` / `get_bone_global_pose` return "the pose you set to the skeleton in the process, the final pose can get overridden by modifiers in the deferred process, if you want to access the final pose, use `SkeletonModifier3D.modification_processed`" - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml)
- Bone metadata (added **4.4**): `get_bone_meta`, `set_bone_meta`, `has_bone_meta`, `get_bone_meta_list` - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml)
- Signals: `pose_updated()` ("Emitted when the pose is updated. - 4.3 breaking changes: signal `bone_pose_changed` replaced by `skeleton_updated` (GH-90575); `BoneAttachment3D.on_bone_pose_update` replaced by `on_skeleton_update` (GH-90575); `add_bone` return type `void` -> `int32` (GH-88791) - [Upgrading to Godot 4.3](https://github.com/godotengine/godot-docs/blob/stable/tutorials/migrating/upgrading_to_godot_4.3.rst)
- DEPRECATED on Skeleton3D (still present in 4.7.2): `set_bone_global_pose_override(bone_idx, pose, amount, persistent = false)`, `get_bone_global_pose_override`, `get_bone_global_pose_no_override`, `clear_bones_global_pose_override`, `physical_bones_start_simulation(bones = [])`, `physical_bones_stop_simulation`, `physical_bones_add_collision_exception`, `physical_bones_remove_collision_exception`, `animate_physical_bones`, and `force_update_all_bone_transforms` ("should only be called internally") - [CR:Skeleton3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Skeleton3D.xml)
- Why override was deprecated (4.3 design article): with global pose override "the processing order between Skeleton3D and AnimationMixer is changed depending on the SceneTree structure", and two nodes using override cannot be chained or reordered. The four override methods are "deprecated (but not removed)" - [Design of the Skeleton Modifier 3D (blog, 12 Aug 2024)](https://godotengine.org/article/design-of-the-skeleton-modifier-3d/)
- **Processing order, from source (4.7.2)**:
  1. `AnimationMixer::_process_animation` runs `_blend_init` -> `_blend_pre_process` -> `_blend_calc_total_weight` -> `_blend_process` -> `_blend_apply` -> `_blend_post_process`, then emits `mixer_applied`. `_blend_apply` writes bones with `Skeleton3D::set_bone_pose_position / _rotation / _scale`. It runs in `NOTIFICATION_INTERNAL_PROCESS` or `NOTIFICATION_INTERNAL_PHYSICS_PROCESS` depending on `callback_mode_process` - [animation_mixer.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/animation/animation_mixer.cpp)
  2. `Skeleton3D` itself receives internal process or internal physics process (per `modifier_callback_mode_process`) and calls `advance(delta)`, which, if there are modifier children, accumulates `update_delta` and requests a deferred update with `UPDATE_FLAG_MODIFIER`. Setting a pose (`_make_dirty`) requests the same deferred update with `UPDATE_FLAG_POSE` (plus `UPDATE_FLAG_MODIFIER` when modifiers exist). The request is `notify_deferred_thread_group(NOTIFICATION_UPDATE_SKELETON)` with the comment "It must never be called more than once in a single frame." - [skeleton_3d.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/skeleton_3d.cpp)
  3. In `NOTIFICATION_UPDATE_SKELETON`: `force_update_all_dirty_bones()`; `_find_modifiers()` (collects children that cast to `SkeletonModifier3D`, in `get_child(i)` order); if any: back up every bone pose and the dirty flags; if `UPDATE_FLAG_MODIFIER` is set call `_process_modifiers()`; if `UPDATE_FLAG_POSE` is not set, abort; else emit `skeleton_updated`; for each skin binding call `RenderingServer::skeleton_bone_set_transform(skeleton, i, global_pose * bind_pose)`; then, if there were modifiers, **restore the unmodified bone poses** and dirty flags - [skeleton_3d.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/skeleton_3d.cpp)
  4. `_process_modifiers()` loops the modifiers in order; for each calls `mod->process_modification(update_delta)`; when `influence < 1.0` it then blends, per bone that the modifier touched, `modifier_pose_cache.interpolate_with(pose_cache, influence)` via `set_bone_pose`; after each modifier it calls `force_update_all_dirty_bones()`; at the end `update_delta = 0` - [skeleton_3d.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/skeleton_3d.cpp)
  5. The modifier list is rebuilt when a `SkeletonModifier3D` child is added, moved or removed (`add_child_notify`, `move_child_notify`, `remove_child_notify` -> `_make_modifiers_dirty`) - [skeleton_3d.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/skeleton_3d.cpp)
- The design article states the same contract: modifiers are "executed only once per frame in the Skeleton3D update process", order "guaranteed to be the same as the order of the children in Skeleton3D's child list"; "Dirty flag resolution may be performed several times per frame, but the update process is a deferred call and is performed only once per frame"; the pose before modification is stored and "when the modification process is complete and applied to the skin, the pose is rolled back"; signals to read poses at each stage: `AnimationMixer.mixer_applied`, `SkeletonModifier3D.modification_processed`, `Skeleton3D.skeleton_updated`; "if the node uses the physics process outside of Skeleton3D and it affects SkeletonModifier3D, the property [modifier_callback_mode_process] must be set to Physics" - [Design of the Skeleton Modifier 3D](https://godotengine.org/article/design-of-the-skeleton-modifier-3d/)
- "The modification by SkeletonModifier3D is immediately discarded after it is applied to the skin, so it is not reflected in the bone pose of Skeleton3D during `_process()`." - [Design of the Skeleton Modifier 3D](https://godotengine.org/article/design-of-the-skeleton-modifier-3d/)

### Inferences
- Gameplay code that needs the final (post-IK) hand or foot position (e.g. to attach a prop or test a grip) must read it inside a `skeleton_updated` or `modification_processed` handler, or use a `ModifierBoneTarget3D` / `BoneAttachment3D`; reading `get_bone_global_pose` in `_process` / `_physics_process` returns the animation-only pose.
- Because modifier results are rolled back each frame, a modifier that needs its own previous output (springs, velocity limits, non-deterministic iterative IK) must keep that state itself; the built-in ones do (see `IterateIK3D.deterministic`, `LimitAngularVelocityModifier3D.reset`).
- If the character body moves in `_physics_process` and IK targets come from physics queries, the consistent setup is AnimationTree `callback_mode_process = PHYSICS` and Skeleton3D `modifier_callback_mode_process = PHYSICS` (the article says so for the modifier side); otherwise the modifiers run on a different tick from the data they read.

### Gaps
- No official statement was found on the cost of the per-frame pose backup / restore for large skeletons.
- The exact text of `set_bone_pose_position` says "local to the Skeleton3D node", which reads oddly for a child bone; not resolved here.

## SkeletonModifier3D: contract, custom modifiers, and every built-in modifier with its version

### Takeaway
A modifier is a child node of `Skeleton3D` that overrides `_process_modification_with_delta(delta)` (4.5+; `_process_modification()` in 4.3-4.4, now deprecated), writes bone poses at 100 %, and lets the skeleton apply `influence`. As of 4.6-4.7 the engine ships look-at, aim, copy / convert transform, twist disperser, angular velocity limit, two-bone / FABRIK / CCD / Jacobian / spline IK with cone joint limits, spring bones, runtime retarget and ragdoll simulator. `SkeletonIK3D` is deprecated.

### Cited Findings
- `SkeletonModifier3D` (inherits `Node3D`): "retrieves a target Skeleton3D by having a Skeleton3D parent. If there is an AnimationMixer, a modification always performs after playback process of the AnimationMixer. This node should be used to implement custom IK solvers, constraints, or skeleton physics." Properties: `active: bool = true`, `influence: float = 1.0` ("This value is used by Skeleton3D to blend, so the SkeletonModifier3D should always apply only 100% of the result without interpolation"). Signal `modification_processed()` ("If you want to get the modified bone pose by the modifier, you must use `Skeleton3D.get_bone_pose` or `get_bone_global_pose` at the moment this signal is fired"). Method `get_skeleton() -> Skeleton3D` - [CR:SkeletonModifier3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/SkeletonModifier3D.xml)
- Virtuals: `_process_modification()` - DEPRECATED "Use `_process_modification_with_delta` instead"; `_process_modification_with_delta(delta: float)` (added **4.5**; "must not apply influence to bone poses because the Skeleton3D automatically applies influence"; "may be called outside `Node._process` and `Node._physics_process` with delta 0.0, since the modification should be processed immediately after initialization of the Skeleton3D"); `_skeleton_changed(old_skeleton, new_skeleton)` (4.5); `_validate_bone_names()` (4.5) - [CR:SkeletonModifier3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/SkeletonModifier3D.xml)
- Source: `SkeletonModifier3D::process_modification(p_delta)` calls `_process_modification(p_delta)` then emits `modification_processed`; the C++ `_process_modification(double)` first tries the script virtual `_process_modification_with_delta`, then falls back to `_process_modification` - [skeleton_modifier_3d.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/skeleton_modifier_3d.cpp)
- Shared enums on the base class: `BoneAxis` (`BONE_AXIS_PLUS_X=0, MINUS_X=1, PLUS_Y=2, MINUS_Y=3, PLUS_Z=4, MINUS_Z=5`; added 4.4); in **4.6** `BoneDirection` (`BONE_DIRECTION_PLUS_X..MINUS_Z = 0..5`, `BONE_DIRECTION_FROM_PARENT = 6`), `SecondaryDirection` (`NONE=0`, `PLUS_X..MINUS_Z = 1..6`, `CUSTOM=7`), `RotationAxis` (`ROTATION_AXIS_X=0, Y=1, Z=2, ALL=3, CUSTOM=4`) moved here from `SpringBoneSimulator3D` (GH-110120, a compatibility break for typed code) - [CR:SkeletonModifier3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/SkeletonModifier3D.xml), [Upgrading to Godot 4.6](https://github.com/godotengine/godot-docs/blob/stable/tutorials/migrating/upgrading_to_godot_4.6.rst)
- Writing a custom modifier in GDScript (official recipe, written for 4.3): `@tool`, `class_name X`, `extends SkeletonModifier3D`; export a bone name with `@export_enum(" ") var bone: String` and fill the hint in `_validate_property` with `skeleton.get_concatenated_bone_names()`; in `_process_modification()` get `get_skeleton()`, `find_bone`, read `skeleton.global_transform * skeleton.get_bone_global_pose(idx)` for world space, write with `skeleton.set_bone_global_pose(idx, ...)`. "`@tool` ... is also required for previewing modifications". "SkeletonModifier3D is a virtual class, so you can't add it as stand alone node". "this method will not be called if the parent is not a Skeleton3D". Per-bone amounts inside one modifier are acceptable; global amount must be left to `influence` - [Design of the Skeleton Modifier 3D](https://godotengine.org/article/design-of-the-skeleton-modifier-3d/)
- "SkeletonModifier3D would be appropriate for effectors and controllers as post FX"; permanent edits (bone editor) should not be modifiers - [Design of the Skeleton Modifier 3D](https://godotengine.org/article/design-of-the-skeleton-modifier-3d/)
- **LookAtModifier3D (4.4+)**: "rotates a bone to look at a target". Order rule: "the LookAtModifier3D assigned to the parent bone must be put above the LookAtModifier3D assigned to the child bone in the list". Properties: `bone`, `bone_name`, `target_node: NodePath`, `forward_axis: int = 4` (+Z), `primary_rotation_axis: int = 1` (Y), `use_secondary_rotation = true`, `relative: bool = false` (added **4.6**: true = rotation applied relative to the pose, false = relative to rest, replacing the pose), `origin_from` (`ORIGIN_FROM_SELF=0`, `ORIGIN_FROM_SPECIFIC_BONE=1`, `ORIGIN_FROM_EXTERNAL_NODE=2`), `origin_bone(_name)`, `origin_external_node`, `origin_offset`, `origin_safe_margin = 0.1`, `duration = 0.0` + `transition_type` + `ease_type` (time-based interpolation, triggered when the target node changes or when an axis flips because of the angle limitation), `use_angle_limitation = false`, `symmetry_limitation`, `primary_limit_angle`, `primary_positive/negative_limit_angle`, `primary_damp_threshold` (and positive / negative variants), the same set for `secondary_*` (angles in radians). Methods `is_target_within_limitation()`, `is_interpolating()`, `get_interpolation_remaining()` - [CR:LookAtModifier3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/LookAtModifier3D.xml)
- **AimModifier3D (4.5+, a BoneConstraint3D)**: "a simple version of LookAtModifier3D that only allows bone to the reference without advanced options such as angle limitation or time-based interpolation ... implemented with smooth tracking without euler". Per-setting methods: `set_forward_axis`, `set_use_euler`, `set_primary_rotation_axis`, `set_use_secondary_rotation`, `set_relative` (4.6) - [CR:AimModifier3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AimModifier3D.xml)
- **BoneConstraint3D (4.5+)**: base class that "modifies the bone set in `set_apply_bone` based on the transform of the bone retrieved by `get_reference_bone`". ### Inferences
- Rockstar-style layer stack maps onto child order under `Skeleton3D`, e.g.: (1) spine lean / bend custom modifier, (2) `TwoBoneIK3D` legs (foot IK, targets from ray / shape casts), (3) custom pelvis offset modifier would have to run BEFORE the leg IK, (4) `TwoBoneIK3D` arms to ledge targets, (5) `BoneTwistDisperser3D` for forearm twist, (6) `LookAtModifier3D` chain spine -> neck -> head (parent first), (7) `LimitAngularVelocityModifier3D` as a pop filter, (8) `PhysicalBoneSimulator3D` last for hit reactions. Each has its own `influence` for blending in and out. This ordering is my design reading of the documented rules (child order = execution order; parent look-at before child), not an official recipe.
- For two-bone limbs `TwoBoneIK3D` is the right choice (deterministic, pole target); iterative solvers default to non-deterministic and rate-limited (2 degrees x 4 iterations per frame), which will visibly lag on fast targets unless tuned.
- `BoneConstraint3D` reference type NODE (4.6) is the built-in route for "hand snaps to a weapon / ledge node" without custom code, as the 4.6 release page describes.

### Gaps
- No manual page (tutorial) for the IK framework exists in the stable (4.7) docs: a search of `tutorials/` for `IKModifier3D` / `TwoBoneIK3D` found nothing; the 4.6 release page says documentation "is in the works". Only the class reference is available.
- Not verified: performance numbers for any modifier; whether `TwoBoneIK3D` rotates the end bone to the target's basis (the XML read here lists no such option).
- `XRHandModifier3D` and the `SpringBoneCollision*` classes were not read in detail.

## AnimationMixer / AnimationPlayer / AnimationTree

### Takeaway
`AnimationMixer` (base of `AnimationPlayer` and `AnimationTree`) owns libraries, blending, root motion and the tick mode. `AnimationTree` nodes are Resources (shared between instances); per-instance state lives in `parameters/...` properties. There is no built-in motion matching, sync markers / phase matching or any warping; the closest tools are blend-space `sync_mode` (4.7), `AnimationNodeAnimation` custom timeline (4.4), state-machine `SWITCH_MODE_SYNC`, and markers (4.4, for sections, not for foot-phase sync).

### Cited Findings
- `AnimationMixer` properties: `active = true`, `callback_mode_process: int = 1` (`ANIMATION_CALLBACK_MODE_PROCESS_PHYSICS=0` "especially useful when animating physics bodies", `IDLE=1`, `MANUAL=2` - use `advance(delta)`), `callback_mode_method: int = 0` (`ANIMATION_CALLBACK_MODE_METHOD_DEFERRED=0` "Batch method calls during the animation process, then do the calls after events are processed", `IMMEDIATE=1`), `callback_mode_discrete` (`DOMINANT=0`, `RECESSIVE=1` default for AnimationPlayer, `FORCE_CONTINUOUS=2` default for AnimationTree), `deterministic: bool` (false on the mixer / player, **true by default on AnimationTree**), `root_node = NodePath("..")`, `root_motion_track`, `root_motion_local` (4.4+), `audio_max_polyphony = 32`, `reset_on_save = true` - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml), [CR:AnimationTree](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationTree.xml)

### Inferences
- Locomotion phase matching: before 4.7 the documented tools are `AnimationNodeAnimation.use_custom_timeline` + `stretch_time_scale` + `start_offset` (author walk / run to the same normalized cycle) and `sync` on blend nodes; from 4.7 `SYNC_MODE_CYCLIC_MUTABLE` on the blend space does the time-scaling automatically. Neither is marker-based (there is no left-foot / right-foot sync marker concept), so clips must be authored to start on the same foot or be offset with `start_offset`.
- Upper / lower body layering: a `Blend2` / `Add2` / `OneShot` with `filter_enabled` and filtered bone paths is the built-in mechanism; with `AnimationTree.deterministic = true` (default) layers whose weights sum below 1 fall back toward the RESET animation, so a RESET animation (rest pose) should exist.
- Animation warping (motion / stride / orientation warping) has to be built by the project: options visible in the API are (a) scale / rotate the root-motion delta before feeding `move_and_slide` (see root motion section), (b) retime with `TimeScale` / `TimeSeek`, (c) a custom `SkeletonModifier3D` or `TwoBoneIK3D` targets to pull hands / feet onto measured contact points, (d) markers in the clip (`get_marker_time`) to know the contact times to warp toward.
- A custom blend node written in GDScript is officially weak (`_process` deprecated, `AnimationNodeExtension` experimental); heavy custom animation logic is safer as a `SkeletonModifier3D` or in C++.

### Gaps
- Performance of large AnimationTrees: no official figures or guidance found in the pages read.
- Maturity of the motion matching addon: only its README was read; the search-result summaries (not opened pages) mention asset-library version 0.2.1 from March 2025, "still under development", and a Godot 4.5.1 forum report of a character that cannot stay still - treat as unverified.
- No godot-proposals issue on motion / stride / orientation warping was found by search; none was read. "How people implement warping in Godot" therefore has no cited source here - the list above is inference.
- `AnimationNodeBlendTree` connection semantics and the manual's blend-tree walkthrough were only skimmed (class list: `add_node`, `connect_node(input_node, input_index, output_node)`, `disconnect_node`, signal `node_changed`).

## Root motion

### Takeaway
Set `AnimationMixer.root_motion_track` to a bone's position / rotation / scale track; the mixer removes that motion from the pose and exposes per-tick deltas (`get_root_motion_position/rotation/scale`) and blended absolute values (`*_accumulator`). The documented CharacterBody3D recipe needs the rotation accumulator unless `root_motion_local` (4.4+) is on.

### Cited Findings
- `root_motion_track: NodePath` - "uses the same format as `Animation.track_set_path`, but note that a bone must be specified. If the track has type TYPE_POSITION_3D, TYPE_ROTATION_3D, or TYPE_SCALE_3D the transformation will be canceled visually, and the animation will appear to stay in place." - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml)
- `root_motion_local: bool = false` (added **4.4**): "If true, `get_root_motion_position` value is extracted as a local translation value before blending. In other words, it is treated like the translation is done after the rotation." - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml), [4.3 XML (member absent)](https://raw.githubusercontent.com/godotengine/godot/4.3-stable/doc/classes/AnimationMixer.xml)
- `get_root_motion_position() -> Vector3`: "motion delta of position"; returns `Vector3(0,0,0)` if the track is not a position track. Basic recipe in the docs: store `current_rotation = get_quaternion()` when the state starts, then `velocity = current_rotation * animation_tree.get_root_motion_position() / delta; set_velocity(velocity); move_and_slide()` - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml)
- Documented "more correct" recipe (accounts for the animation's own rotation): `set_quaternion(get_quaternion() * animation_tree.get_root_motion_rotation())` then `var velocity = (animation_tree.get_root_motion_rotation_accumulator().inverse() * get_quaternion()) * animation_tree.get_root_motion_position() / delta; set_velocity(velocity); move_and_slide()` - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml)
- With `root_motion_local = true` the position "returns the pre-multiplied translation value with the inverted rotation" and the recipe becomes: `set_quaternion(get_quaternion() * animation_tree.get_root_motion_rotation())`; `var velocity = get_quaternion() * animation_tree.get_root_motion_position() / delta` - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml)
- `get_root_motion_rotation() -> Quaternion` (delta; identity if not a rotation track); `get_root_motion_scale() -> Vector3` (delta; zero vector if not a scale track; the docs' example accumulates `scale_accum += get_root_motion_scale()`) - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml)
- `get_root_motion_position_accumulator()`, `get_root_motion_rotation_accumulator()`, `get_root_motion_scale_accumulator()`: "the blended value of the ... tracks"; useful "where you want to respect the initial key values of the animation"; the rotation accumulator "is necessary to apply the root motion position correctly, taking rotation into account". Each carries the warning: "if the animation loops, an unintended discrete change may occur, so this is only useful for some simple use cases" (this warning is on differencing accumulators yourself) - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml)
- The documented examples all run in `_process(delta)` and divide by that `delta` - [CR:AnimationMixer](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationMixer.xml)
- Manual: selecting the bone as root motion track "will cancel the bone transformation visually (the animation will stay in place)"; the motion "can be fed to functions such as CharacterBody3D.move_and_slide"; `RootMotionView` is a tool node that acts as a custom floor (disabled in game) - [Using AnimationTree (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/animation/animation_tree.rst)
- `RootMotionView` (inherits `VisualInstance3D`, editor-only, hidden in the running project): `animation_path` (to an AnimationMixer), `cell_size = 1.0`, `color`, `radius = 10.0`, `zero_y = true` - [CR:RootMotionView](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/RootMotionView.xml)
- `SkeletonProfile.root_bone`: "A bone name that will be used as the root bone in AnimationTree. This should be the bone of the parent of hips that exists at the world origin." In `SkeletonProfileHumanoid` the tree starts `Root -> Hips` - [CR:SkeletonProfile](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/SkeletonProfile.xml), [CR:SkeletonProfileHumanoid](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/SkeletonProfileHumanoid.xml)
- `Skeleton3D.motion_scale` multiplies position tracks; import option "Normalize Position Tracks" stores the `scale_base_bone` (Hips) height as `motion_scale` so root / hips translation scales with character height - [Retargeting 3D Skeletons (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.rst)
- `AnimationNodeTimeSeek.explicit_elapse = true` (4.4+) makes seeks process keys in between, "such as calculating root motion" - [CR:AnimationNodeTimeSeek](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/AnimationNodeTimeSeek.xml)
- `move_and_slide()` "should be used in `Node._physics_process`"; `velocity` is in units per second - a "common mistake is setting this property to the desired velocity multiplied by delta" - [CR:CharacterBody3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/CharacterBody3D.xml)

### Inferences
- Tick mismatch pitfall: root-motion deltas are per mixer update. If the tree runs on idle (default `callback_mode_process = 1`) but the body moves in `_physics_process`, deltas are produced at render rate and consumed at physics rate, so motion is lost or doubled. For a CharacterBody3D the consistent setup is `callback_mode_process = ANIMATION_CALLBACK_MODE_PROCESS_PHYSICS` and reading the delta in `_physics_process` with the physics delta (the class reference itself says the physics mode is "especially useful when animating physics bodies"). The doc examples use `_process` only for brevity.
- Blending pitfall: by default the position delta is blended in the root track's own space while each clip may have rotated differently - that is what the accumulator recipe and `root_motion_local` (4.4+) address; on 4.4+ `root_motion_local = true` gives the simpler `get_quaternion() * position` form.
- Motion warping hook: because root motion arrives as a plain per-tick `Vector3` / `Quaternion` before it is applied, a vault / climb clip can be warped by scaling or re-aiming that delta between two marker times so the body lands on the measured obstacle, then correcting hands / feet with IK modifiers. (Inference from the API; no official recipe.)
- A root bone at the origin / foot level (profile "Root") is needed; using "Hips" as the root motion track would also strip hip sway.

### Gaps
- No official text was found on root motion with `AnimationNodeBlendSpace` sync modes, on how looping affects the delta getters (only the accumulators carry the loop warning), or on root motion under physics interpolation.
- Vertical (Y) root motion handling for climbs with `CharacterBody3D` (gravity, floor snap) is not documented in the pages read.

## Retargeting and import

### Takeaway
Animation sharing is done at import time: map the skeleton to `SkeletonProfileHumanoid` with a `BoneMap`, let the importer rename bones and overwrite rests to the profile's reference pose; runtime retargeting between skeletons with different rests is `RetargetModifier3D` (4.4+). FBX is imported natively through ufbx since 4.3.

### Cited Findings

## Ragdoll, partial ragdoll and active ragdoll

### Takeaway
Ragdoll = a `PhysicalBoneSimulator3D` (a `SkeletonModifier3D`) with `PhysicalBone3D` children; start with `physical_bones_start_simulation(bone_names)`, blend with the simulator's `influence`. `PhysicalBone3D` joints (pin, cone, hinge, slider, 6DOF) expose limits but no motors, so a powered ragdoll needs script torques or a parallel rig of `RigidBody3D` + `Generic6DOFJoint3D`; Jolt (default for new projects since 4.6) ignores the joints' soft-limit parameters.

### Cited Findings
- Setup: `PhysicalBoneSimulator3D` "is the parent of all physical bones and is responsible for controlling the simulation"; one `PhysicalBone3D` child per simulated bone. Editor: select `Skeleton3D` -> skeleton button -> "Create Physical Skeleton" generates bones, collision shapes and pin joints - [Ragdoll system (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/physics/ragdoll_system.rst)
- `PhysicalBoneSimulator3D` (inherits `SkeletonModifier3D`; API unchanged 4.3 -> 4.7.2): `physical_bones_start_simulation(bones: StringName[] = [])` ("Optionally, a list of bone names can be passed-in, allowing only the passed-in bones to be simulated"), `physical_bones_stop_simulation()`, `physical_bones_add_collision_exception(RID)`, `physical_bones_remove_collision_exception(RID)`, `is_simulating_physics()` - [CR:PhysicalBoneSimulator3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/PhysicalBoneSimulator3D.xml)
- Partial ragdoll: pass "the bone names (not the PhysicalBone3D node names)", e.g. `physical_bones_start_simulation(["l-arm", "r-arm"])`; "nonexistent bone names will not print any error or warning" (whole body may ragdoll instead). "To control how strongly the partial ragdoll simulation affects the overall animation, you can adjust the Influence property in the PhysicalBoneSimulator3D node ... By default, it's set to 1.0, which means the ragdoll simulation fully overrides the rest of the animation." - [Ragdoll system (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/physics/ragdoll_system.rst)
- Source: in `_process_modification`, for each bone with a physical bone - if it is not simulating, the physical bone follows the animated pose (`_bone_pose_updated`, `reset_to_rest_position`); if simulating, `skeleton->set_bone_global_pose(i, bones[i].global_pose)` (the simulated pose). The simulator also listens to `Skeleton3D.pose_updated` - [physical_bone_simulator_3d.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/physics/physical_bone_simulator_3d.cpp)
- `PhysicalBone3D` (inherits `PhysicsBody3D`; API unchanged 4.3 -> 4.7.2): `joint_type` (`JOINT_TYPE_NONE=0, PIN=1, CONE=2, HINGE=3, SLIDER=4, 6DOF=5`), `joint_offset: Transform3D`, `joint_rotation: Vector3` (radians), `body_offset: Transform3D`, `mass = 1.0`, `friction = 1.0`, `bounce = 0.0`, `gravity_scale = 1.0`, `linear_damp`, `angular_damp` (+ `*_damp_mode`: `DAMP_MODE_COMBINE=0`, `REPLACE=1`), `linear_velocity`, `angular_velocity`, `can_sleep = true`, `custom_integrator = false`; `apply_central_impulse(impulse)`, `apply_impulse(impulse, position)`, virtual `_integrate_forces(state: PhysicsDirectBodyState3D)`; `get_bone_id()`, `is_simulating_physics()`. Raycasts hit physical bones only if the parent simulator's `active` is true and the bone is assigned (`get_bone_id() >= 0`) - [CR:PhysicalBone3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/PhysicalBone3D.xml)
- Per joint type the inspector exposes `joint_constraints/...`: pin - `bias`, `damping`, `impulse_clamp`; cone - `swing_span`, `twist_span`, `bias`, `softness`, `relaxation`; hinge - `angular_limit_enabled`, `angular_limit_upper`, `angular_limit_lower`, `angular_limit_bias`, `angular_limit_softness`, `angular_limit_relaxation`; slider - linear / angular limit upper / lower / softness / restitution / damping. The string "motor" does not occur anywhere in `physical_bone_3d.cpp` - [physical_bone_3d.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/physics/physical_bone_3d.cpp)
- Joint advice: default is an unconstrained PinJoint which "Leads to 'crumpling' of the bones, so it's recommended to use other joint types for most characters"; ConeJoint for shoulders, hips, neck (Swing Span 20-90 degrees, Twist Span 20-45 degrees); HingeJoint for elbows and knees (enable Angular Limit); 6DOF "most powerful ... but also the most complex to configure". Adjust joints before collision shapes. Remove tiny / utility bones (each PhysicalBone3D has a cost; one bone for a whole hand) - [Ragdoll system (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/physics/ragdoll_system.rst)
- Collision setup: set layers / masks so the CharacterBody3D capsule does not collide with its own (inactive) ragdoll - otherwise "the player [can] wildly bounce around or get stuck"; collision exceptions by code via the simulator methods - [Ragdoll system (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/physics/ragdoll_system.rst)

- `Generic6DOFJoint3D` (standalone joint node between two bodies): per axis `angular_motor_x/enabled` (false), `angular_motor_x/target_velocity` (0.0), `angular_motor_x/force_limit` (300.0) (same for y, z, and linear motors); springs `angular_spring_x/enabled`, `/stiffness`, `/damping`, `/equilibrium_point` (and `linear_spring_*`); params `PARAM_ANGULAR_MOTOR_TARGET_VELOCITY=17`, `PARAM_ANGULAR_MOTOR_FORCE_LIMIT=18`; flags `FLAG_ENABLE_ANGULAR_LIMIT=1`, `FLAG_ENABLE_MOTOR=4`, `FLAG_ENABLE_LINEAR_MOTOR=5` - [CR:Generic6DOFJoint3D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Generic6DOFJoint3D.xml)
- Jolt vs Godot Physics on joints: Jolt does not support PinJoint3D `bias`, `damping`, `impulse_clamp`; HingeJoint3D `bias`, `softness`, `relaxation`; SliderJoint3D `angular_*`, `*_limit/softness`, `*_limit/restitution`, `*_limit/damping`; ConeTwistJoint3D `bias`, `relaxation`, `softness`; Generic6DOFJoint3D `*_limit_*/softness`, `/restitution`, `/damping`, `/erp` ("a warning is emitted if you set these properties to anything but their default values"). - Jolt: added as built-in alternative in 4.4; "By default, new projects will use it"; `physics/3d/physics_engine` values `DEFAULT` ("currently equivalent to GodotPhysics3D"), `GodotPhysics3D`, `Jolt Physics` ("generally faster and more reliable than GodotPhysics3D ... the default for projects created starting in Godot 4.6"), `Dummy` - [Using Jolt Physics (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/physics/using_jolt_physics.rst), [CR:ProjectSettings](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/ProjectSettings.xml)
- Jolt contact impulses from `PhysicsDirectBodyState3D.get_contact_impulse()` are estimated ahead of time and only accurate when the two bodies touch nothing else (relevant to impact-driven hit reactions) - [Using Jolt Physics (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/physics/using_jolt_physics.rst)
- Community (forum, Sep 2026, Godot 4.6.2): user asks where the motor parameters are on a 6DoF `PhysicalBone3D` - "it doesn't have the motor parameters i need ... the spring parameters just never worked for me"; reply: "I couldn't find one either. You could simulate the motor in script or with a C++ gdextension function" - [forum thread 144270](https://forum.godotengine.org/t/where-is-the-motor-parameters-in-the-6dof-physicalbone3d-node/144270)
- Community (forum, Nov 2025, Godot 4.5): hit reaction by `physical_bones_start_simulation()`, `influence = 0.8`, then tween `influence` to 0.0 over 0.5 s and `physical_bones_stop_simulation()`; original code set `animation_tree.active = false` during the ragdoll - the poster confirmed that NOT deactivating the AnimationTree "does indeed look better" - [forum thread 128728](https://forum.godotengine.org/t/active-ragdoll-in-godot-4-5-how-to-achieve-good-results/128728)
- Community (forum, Jul-Oct 2025, Godot 4.4.1 + Jolt): per-bone hit reaction by switching simulation on for the hit bone then off makes the body part snap back to the animation; a responder reports spring stiffness can make the physics character closely match the animation, "a couple of implementations were unstable in jolt", and notes the spring / damper coefficients used were shared by all joints - [forum thread 117047](https://forum.godotengine.org/t/active-ragdolls-in-godot-jolt-is-it-even-possible/117047)
- Community plugin (Godot 3-era, README mentions Bullet): `R3X-G1L6AME5H/Godot-Active-Ragdolls` replaces PhysicalBones with `RigidBody` + `Generic6DOFJoint`, one skeleton plays the animation and the physics rig's joints try to match its rotations ("Matching Velocity" multiplier); the README states "if you are trying to implement something special like Active Ragdolls, you will find PhysicalBones to be unsatisfactory" - [Godot-Active-Ragdolls README](https://raw.githubusercontent.com/R3X-G1L6AME5H/Godot-Active-Ragdolls/main/README.md)

### Inferences
- Blend ragdoll -> animation: there is no pose-capture ("get up from ragdoll pose") helper on the simulator; the documented lever is `influence`. A get-up needs: read the simulated bone poses at `modification_processed` / `skeleton_updated`, pick a get-up clip by body orientation, move the CharacterBody3D to the ragdoll's pelvis, then fade `influence` to 0 while the clip plays (`AnimationMixer.capture` only applies to tracks flagged `UPDATE_CAPTURE` under AnimationPlayer). This is a design inference, not a documented recipe.
- Hit reactions: keep the AnimationTree running, start simulation on a bone subset (e.g. spine + arm), apply `PhysicalBone3D.apply_impulse`, and tween simulator `influence` 0.8 -> 0 (pattern from the forum thread). Because `influence` is one value per simulator, different per-limb weights need either several simulators or a custom modifier.
- Active / powered ragdoll (Euphoria-like balance) is not available out of the box: `PhysicalBone3D` has no motors; options are (a) torques in `PhysicalBone3D._integrate_forces` (PD controller toward the animated pose), or (b) a separate `RigidBody3D` + `Generic6DOFJoint3D` rig using angular motors / springs, copied back to the skeleton by a custom `SkeletonModifier3D`. With Jolt, limits are hard (soft-limit parameters ignored), so tuning made for Godot Physics does not carry over.

### Gaps
- Whether Jolt honours `Generic6DOFJoint3D` angular motors and springs (`angular_motor_*`, `angular_spring_*`) was NOT verified: the manual only lists the unsupported limit properties; the Jolt module source was not read.
- No GitHub issue about PhysicalBone3D problems under Jolt (stretching, inverted limits) was opened; a search summary mentioned godot issue #84468 and a godot-jolt discussion #825 about inverted angular limit gizmos - unverified.
- No maintained Godot 4.6+ active-ragdoll project was found; the one plugin read is for Godot 3 / Bullet.
- The official `3d/ragdoll_physics` demo project was not opened.

## CharacterBody3D, stairs, physics queries, physics interpolation, tick rate

### Takeaway
`CharacterBody3D.move_and_slide()` handles floors, slopes, walls and moving platforms but has no step-up; stairs are done with `test_move` / `PhysicsServer3D.body_test_motion` sweeps (or a `SeparationRayShape3D`). 3D physics interpolation exists since 4.4 (SceneTree-side since 4.5) and requires all movement, including animation and modifiers that move things, to happen on the physics tick, with the camera interpolated manually.

- Debug: in 3D, Debug > Visible Collision Shapes does NOT take physics interpolation into account (shapes appear slightly ahead of the visuals) - [Using physics interpolation (manual)](https://github.com/godotengine/godot-docs/blob/stable/tutorials/physics/interpolation/using_physics_interpolation.rst)

### Inferences
- Skeleton and interpolation: interpolation is applied to node transforms; bone poses are not node transforms, so a skeleton animated on the physics tick is posed at tick rate while its root node glides smoothly. Whether that is visible depends on tick rate; options are a higher tick rate, or animating on idle while moving the body on physics (then root motion must be bridged between the two ticks). No official statement on this was found - treat as an open design risk to test at 10-30 TPS.
- `BoneAttachment3D` has interpolation OFF by default (default `physics_interpolation_mode = 2` in its XML since 4.5), consistent with attachments following the per-frame skeleton update rather than physics ticks.
- For Rockstar-style traversal (vault / climb detection) the query set is: `ShapeCast3D` or `cast_motion` forward at chest height, `intersect_ray` downward from above the obstacle for ledge height / normal, `get_rest_info` / `collide_shape` for clearance on top, `test_move` for the landing spot. Under Jolt, prefer ray normals over shape-query normals at edges (docs warn about margin-induced odd normals).

## Tooling for traversal authoring (tracks, markers, method calls, debugging)

### Takeaway
Contact events can be authored as method-call tracks (deferred or immediate) or as named markers (4.4+) that code reads by time; the animation editor in 4.7 gained collapsible track groups. Built-in visual debugging for the animation stack is thin: `RootMotionView`, skeleton gizmos, visible collision shapes.

### Cited Findings
- `Animation.TrackType`: `TYPE_VALUE=0`, `TYPE_POSITION_3D=1`, `TYPE_ROTATION_3D=2`, `TYPE_SCALE_3D=3`, `TYPE_BLEND_SHAPE=4`, `TYPE_METHOD=5` ("Method tracks call functions with given arguments per key"), `TYPE_BEZIER=6`, `TYPE_AUDIO=7`, `TYPE_ANIMATION=8`. `UpdateMode`: `UPDATE_CONTINUOUS=0`, `UPDATE_DISCRETE=1`, `UPDATE_CAPTURE=2`. `LoopMode`: `LOOP_NONE=0`, `LOOP_LINEAR=1`, `LOOP_PINGPONG=2` - [CR:Animation](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/doc/classes/Animation.xml)
